## P0-A. 순환 대기 교착 — 선수들이 서로를 영구히 기다린다

### 측정 `[측정]`

20경기의 모든 스냅샷에서 "누가 누구를 기다리는지" 방향 그래프를 만들어 순환을 탐지했다.

```
대기 상태가 있던 틱 4,851 / 그중 순환 대기가 존재한 틱 729 (15.0%)
최장 대기 사슬 3명
'문 통과 순서 대기'(문 예약) 유닛-틱 3,360

순환 사례:
  t=0.5s  MAGPIE → ARBEL → MAGPIE
  t=0.6s  MAGPIE → ARBEL → MAGPIE
  t=0.7s  MAGPIE → ARBEL → MAGPIE
  ...
```

40경기 별도 측정에서는 사슬이 4단까지 관찰됐다.

```
MAGPIE hold / 통과 순서 대기 · AUBERT 선행
AUBERT hold / 통과 순서 대기 · 해동 선행
해동    hold / 문 통과 순서 대기 · 동료 통행 확보
ARBEL  hold / 통과 순서 대기 · MAGPIE 선행
```

MAGPIE는 AUBERT를, AUBERT는 해동을, 해동은 문 예약을 기다리고, ARBEL은 MAGPIE를 기다린다. 앞이 뚫리지 않으므로 전원이 멈춘다.

부수 지표

| 지표 | 값 |
|---|---|
| 통과 순서 대기 | 살아있는 시간의 **9.0%** |
| 최장 연속 대기 | **132.9초** |
| 40cm 이내에서 동시에 대기한 쌍 | 8,908회 |
| 30초 이상 한 자리 고착(라운드 종료 시) | 36/400명 |
| 공격 전원 hold | 전체 틱의 15.6% |

**t=0.5초에 이미 순환이 시작된다.** 스폰 직후 진입구 앞에서 발생하며, 이는 다섯 명이 26.7단위(0.67m) 간격으로 일렬로 서는 기존 문제(QA P2-20)의 직접적 결과다.

### 원인 `[코드]`

`TacticalRealtimeSimulation.ts:1642` 부근의 동료 회피 로직이다.

```ts
const blocker = units
  .filter(c => c.alive && c.side === unit.side && c.id !== unit.id)
  .filter(c => distance(c.position, next) < TEAMMATE_CLEARANCE)
  .sort((l, r) => l.id.localeCompare(r.id))[0];
if (blocker) {
  const following = blocker.velocity.x*dx + blocker.velocity.y*dy > 0 && ...;
  const detour = !following && (plan.detourUntil ?? 0) <= now && candidates.find(...);
  if (detour) { ... }
  else if (unit.action !== 'reload') {
    this.holdMovement(unit, `통과 순서 대기 · ${blocker.callSign} 선행`, yieldUntil, now, 0.2, log);
  }
  return;
}
```

네 가지가 겹친다.

1. **우선권이 없다.** A와 B가 서로를 `blocker`로 볼 수 있고, 둘 다 양보한다. 양보 방향을 정하는 규칙이 없으므로 순환이 구조적으로 가능하다.
2. **멈춘 동료는 영구 장애물이 된다.** `following`은 blocker가 같은 방향으로 **움직일 때만** 참이다. 이미 대기 중이라 속도가 0인 동료에게는 거짓이 되어, 대기자가 뒤의 전원을 막는 벽이 된다. 이것이 사슬을 만든다.
3. **우회가 좁은 곳에서 항상 실패한다.** `detour` 후보는 경로 전 구간에서 **모든 아군이 `TEAMMATE_CLEARANCE` 이상 떨어져 있어야** 유효하다. 폭 80단위 문에 다섯 명이 26.7단위 간격으로 몰려 있으면 유효한 후보가 없다. 즉 요충지에서는 언제나 `hold`로 떨어진다.
4. **탈출 조건이 없다.** `holdMovement(..., 0.2)`는 0.2초 뒤 같은 판정을 반복한다. 대기 누적 시간을 보지 않으므로 타임아웃도, 우선권 승격도, 다른 포털로의 재경로도 없다.

추가로 `sort(id.localeCompare)`는 **임의의** 동료를 blocker로 고른다. 가장 가까운 것도, 실제로 막고 있는 것도 아니다. 그래서 로그에 표시되는 "○○ 선행"이 실제 장애물과 다를 수 있다.

### 수정 방향

- **고정 우선권**: 각 유닛에 안정적인 순위(`formationIndex`)를 주고, **자기보다 순위가 낮은 blocker에게만 양보**한다. 순환은 누군가 높은 순위에게 양보해야 성립하므로 구조적으로 사라진다.
- **대기 타임아웃**: 누적 대기가 1.5초를 넘으면 `TEAMMATE_CLEARANCE` 허용치를 일시적으로 줄여 밀고 지나가거나, 다른 포털로 재경로한다.
- **blocker 선택을 실제 방해도 기준으로**: `id.localeCompare` 대신 `next`까지의 거리 또는 경로 선분과의 거리로 고른다.
- **진입 시차**: 다섯 명이 한 문에 동시에 도달하지 않게 스폰 간격을 넓히고 진입 지연을 준다. QA P2-20과 같은 작업이다.

## P1-C. 고유 능력이 고유하지 않다 `[측정]` `[코드]`

45경기에서 utility 사건을 오퍼레이터별로 셌다. 플래그가 아니라 실제 사건 기준이다.

```
카메라 설치 (MARCHAND의 고유 능력)
  MARCHAND  45회   ← 본인
  HALLORAN  45회   ← 남의 능력
  성곽       45회   ← 남의 능력
  REUSS     20회   ← 남의 능력
  SAVELLI    4회   ← 남의 능력

연막 투척 (ARBEL의 고유 능력)
  AUBERT    38회   ← 남의 능력이 본인보다 많다
  ARBEL     35회   ← 본인
  COLLIER   23회
  MAGPIE     7회
  해동        4회
```

### 원인 `[코드]`

`TacticalRealtimeSimulation.ts:899~918`의 조건이 **오퍼레이터가 아니라 역할(role)** 로 가젯을 배포한다.

```ts
// 카메라 (900행)
me.operator.role === 'BLOCKING' || me.operator.role === 'DEFENSIVE_SETUP'
  || (input.defensePreparation === 'camera' && unit.formationIndex === input.defenders.length - 1)
```

BLOCKING = MARCHAND, HALLORAN. DEFENSIVE_SETUP = REUSS, 성곽, SAVELLI. **수비 오퍼레이터 6명 중 BRANDT를 뺀 5명 전원이 카메라를 갖는다.**

```ts
// 연막 (906행)
input.attackStyle === 'smoke' || me.operator.role === 'SEARCH'
  || unit.id === objectiveState.carrierId
  || (skills.distancePreference < 40 && gap > comfortableDistance)
```

SEARCH = ARBEL, AUBERT. 게다가 `attackStyle === 'smoke'`면 공격 전원, 장치 운반자면 누구나, 근거리 선호 선수면 누구나 연막을 던진다.

```ts
// 파쇄 (920행)
unit.side === '공격' && (unit.callSign === 'MEDVED' || (input.attackStyle === 'breach' && me.operator.role === 'ENTRY'))
```

MAGPIE·해동도 breach 스타일에서 파쇄한다. 다만 **보강된 벽을 뚫는 것은 MEDVED만** 가능하므로(`!wall.reinforced || callSign === 'MEDVED'`) 이 부분의 고유성은 유지된다.

```ts
// 수류탄 (916행) — 오퍼레이터·역할 제약이 아예 없다. 공격 전원.
```

### 영향

QA P1-08(총기 파지 어긋남)과 P1-06(진영 색이 2×4단위 점 하나)에 이어, **기능면에서도 12명이 구분되지 않는다.** 외형으로도 구분이 안 되고 하는 일도 같으면 오퍼레이터 선택이 의미를 잃는다.

### 수정 방향

역할 기준을 오퍼레이터 기준으로 좁힌다. 공용으로 남길 것과 고유로 돌릴 것을 나눈다.

- **고유로**: 카메라 → MARCHAND만. 연막 → ARBEL만. 파쇄 → MEDVED만
- **공용으로 유지**: 수류탄 (전원 1개씩)
- `defensePreparation`의 '관측 카메라' 옵션은 MARCHAND가 편성에 없을 때의 대체 수단으로 남기되, MARCHAND가 있으면 중복 지급하지 않는다

## P1-D. 가젯 하나를 쓰면 나머지 전부 잠긴다 `[코드]`

카메라·연막·수류탄·파쇄 네 분기가 **하나의 플래그** 안에 들어 있고, 각 분기가 그 플래그를 세운다.

```ts
if (!unit.utilityUsed && unit.reloadRemaining <= 0 && now > .2) {
  if (/* 카메라 */) { ... unit.utilityUsed = true; ... continue; }
  if (/* 연막 */)  { ... unit.utilityUsed = true; ... continue; }
  if (/* 수류탄 */) { ... unit.utilityUsed = true; ... continue; }
  if (/* 파쇄 */)  { ... unit.utilityUsed = true; ... continue; }
}
```

결과

- 연막을 던진 공격수는 그 라운드에 **수류탄을 던질 수 없고 파쇄도 할 수 없다**
- 카메라를 설치한 수비수는 그 라운드에 다른 어떤 가젯도 쓸 수 없다
- 오퍼레이터 설명에 있는 "두 발 소지한다"(MAGPIE 경첩 절단 산탄) 같은 수량 개념이 코드에 반영되지 않는다

**수정 방향**: 플래그 하나를 종류별 잔여 수량으로 바꾼다. `utility: { smoke: 1, grenade: 1, breach: 2, camera: 1 }` 형태면 기존 조건문 구조를 그대로 두고 `!unit.utilityUsed`만 `remaining(kind) > 0`으로 바꾸면 된다.

## P2 — 동작 품질

### P2-E. 최대 회전속도 포화 11.0% `[측정]`

살아있는 시간의 **11.0%** 동안 몸이 초당 240도(`TURN_SPEED = 4π/3`)에 근접한 속도로 돌고 있다. 관전 화면에서 팽이처럼 보이는 구간이다. 회전 목표가 매 틱 바뀌면서 회전이 수렴하지 않는다는 뜻이다.

관련 지표: `goal` 변경 초당 0.29회, `action` 변경 초당 0.40회 — 2.5초에 한 번씩 하는 일이 바뀐다.

### P2-F. 몸 반대 방향으로 이동 4.4% `[측정]`

이동 중인 틱의 4.4%에서 이동 방향과 몸 방향이 90도 이상 어긋난다. 뒤를 보며 걷는 구간이며, 시야 판정이 `facing` 기준이므로 **가는 방향을 못 보면서 이동한다.**

### P2-G. 부들거림과 제자리 맴돌기 `[측정]`

| 지표 | 값 |
|---|---|
| 방향 반전(연속 두 틱의 속도 내적이 음수) | 경기당 24.1회, 이동 틱의 1.1% |
| 제자리 맴돌기(3초 창에서 순변위/이동거리 < 0.3) | 4.7% |

기존 백로그의 "부들거림"은 실재하며 이동 틱의 1.1% 규모다. 심각하지는 않지만 우회 로직(`detourUntil = now + 1.5`)이 1.5초마다 새 우회를 삽입하면서 생기는 것으로 보인다.

### P2-H. 교전 중 재장전 63.6% `[측정]`

재장전 22회 중 14회가 **적이 자기 팀 시야에 보이는 상태**에서 일어났다. 표본이 작지만(라운드가 짧고 치명적이라 재장전 자체가 드물다) 판단 규칙이 없다는 뜻이다. 엄폐 여부나 잔탄 여유를 보지 않는다.

### P2-I. 보강 완료율 48% `[측정]`

```
REUSS / fortification-started  25~30회
REUSS / wall-reinforced        12회
SAVELLI / fortification-started 5회
SAVELLI / wall-reinforced       3회
```

시작한 보강의 절반 이하만 완료된다. 2초 설치 중 중단되는 원인(교전, 경로 재탐색, 대기)을 확인해야 한다. 준비 단계의 선택이 실제로 반영되지 않는다는 의미다.

| 1 | **P0-A 순환 대기** — 고정 우선권 + 대기 타임아웃 | 함수 1개 | 30초 고착 9%와 전원 hold 15.6%가 함께 줄어든다. 기존 QA의 선발조 교착(P0-01)과 같은 뿌리다 |
| 2 | **P1-D 가젯 잠김** — 플래그를 종류별 수량으로 | 조건문 4곳 | 즉시 가젯 사용량이 늘고 라운드가 다양해진다 |
| 3 | **P1-C 고유 능력** — 역할 조건을 오퍼레이터 조건으로 | 조건문 3곳 | 오퍼레이터 선택이 의미를 갖는다 |
| 4 | **P2-E/F 회전·역주행** — 회전 목표를 이동 방향에 고정, goal 변경에 최소 유지 시간 | 중간 | 관전 화면의 어색함이 줄어든다 |
| 5 | **P2-H 재장전 판단** — 엄폐 중이거나 잔탄 여유가 있을 때만 | 조건 1개 | 표본이 작아 효과 확인에 경기 수가 필요하다 |

1번과 2번은 합쳐서 반나절이면 끝나고 체감 변화가 가장 크다.

**1번은 기존 QA의 P0-01(선발조 합류 좌표 교착)과 같은 대기 메커니즘을 쓴다.** 두 건을 따로 고치지 말고 함께 설계하는 편이 낫다. 층간 교전의 계단도 같은 큐를 타므로, 이 수정 없이 계단을 넣으면 계단마다 같은 교착이 생긴다.

## 재현 방법

각 수치는 아래 방식으로 다시 측정할 수 있다.

- 실제 `TeamGenerator` → `completeOperatorDraft` → `confirmOperatorDraft`로 편성하고 `TacticalRealtimeSimulation.run()`을 호출
- `scoutPlan: { indices: [], seconds: 25, entryRoute: g % 5 }`을 **반드시 포함** (실제 UI가 타는 경로)
- `result.snapshots`의 유닛별 `position` · `velocity` · `facing` · `action` · `goal` · `traversal`을 틱 단위로 집계
- 순환 대기는 `goal`의 `통과 순서 대기 · (\S+) 선행` 패턴으로 방향 그래프를 만들어 탐지
- 능력 사용률은 `result.events` 중 `type === 'utility'`를 actor의 콜사인으로 묶어 집계

팀 능력치는 생성기 난수이므로 실행마다 절대값이 달라진다. 비율과 패턴을 비교한다.
