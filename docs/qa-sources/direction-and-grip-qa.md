# 1부. 설계 방향 — "경기 전 직관적 선택 후 관전"과 현재 구현의 충돌

## 1-1. 이번 패치가 반대 방향으로 갔다 `[화면]`

관전 화면 하단에 **경기 중 감독 지시 버튼이 새로 추가됐다.**

```
[진입] [대기] [후퇴] [진입로 1 ▾] [경로 변경]
```

이전 QA에서 P0-03으로 "엔진은 `push/hold/retreat/route`를 지원하는데 UI가 없다"고 보고한 항목이고, 이번 패치가 그것을 구현했다.

**그런데 이 방향은 지금 원하는 것과 정반대다.** 경기 중 조작이 생기면 감독은 관전자가 아니라 실시간 조작자가 된다. "경기 전에 정하고 경기는 본다"를 원한다면 이 버튼들은 제거 대상이다.

판단이 필요한 지점이다. 둘 중 하나를 골라야 하고 둘 다 가질 수는 없다.

| 방향 | 감독의 역할 | 경기 중 조작 | 긴장의 출처 |
|---|---|---|---|
| A. 사전 결정형 (지금 원하는 것) | 준비 단계의 선택 | 배속·시점만 | "내 선택이 맞았나" |
| B. 실시간 지휘형 (패치가 간 방향) | 상황 대응 | 진입·대기·후퇴·경로 | "지금 무엇을 시킬까" |

A를 고른다면 이번에 추가된 지시 버튼은 되돌리고, 그 노력을 준비 화면으로 옮겨야 한다.

## 1-2. 준비 화면이 직관적이지 않다 `[측정]`

실제 화면의 조작 요소를 셌다.

```
버튼·셀렉트·체크박스 합계  28개
```

내역: 진입구 5 · 진입 방식 3 · 분산 진입 체크 1 · 설치 목표 2 · 거점 마지막 진입 셀렉트(4항목) · 수색 시간 셀렉트(4항목) · 선수 카드 5 · 선발조 배정 체크 5 · 자동 배정 1 · 장비 카드 · 뒤로 · 출전

조합 수를 계산하면

```
진입 방식 3 × 진입구 5 × 사이트 2 × 거점 진입 4 × 수색 시간 4
  × 선발조 인원 조합 26(0~3명) = 12,480가지
(분산 진입과 오퍼레이터 편성은 제외한 수)
```

**출전 버튼을 누르기 전에 12,480가지 중 하나를 고르고 있다.** 유저가 "알아서 잘 내가 원하는 방향으로"를 기대하는 지점에서 요구되는 결정량이 이 규모면, 대부분은 아무거나 누르고 넘어가거나 화면을 떠난다.

## 1-3. 노출된 숫자가 8개다 `[화면]`

한 선수를 선택하면 아래가 표시된다.

```
Deseny · 조준 96 / 숙련 67 / 공격성 64
전술 인지: 가까운 교전 선호 · 위험 확인 60
총기 운용: 초탄 조준 96 · 반동 제어 67
반응·가젯: 반응 83 · 가젯 타이밍 75
```

프로젝트 원칙은 "숨은 평정심·팀 궁합은 숫자로 공개하지 않는다"인데, 그 원칙을 지키면서도 **8개의 다른 숫자를 공개하고 있다.** 숫자를 감추는 규칙이 하나 있다는 사실이 나머지를 공개해도 된다는 근거가 되지 못한다.

시뮬레이션 게임의 숫자는 "이 값을 올리면 무엇이 좋아지는가"를 유저가 계산할 때 의미가 있다. 지금은 감독이 그 값을 바꿀 수단이 없으므로, 8개 숫자는 읽고 넘기는 정보이지 선택의 근거가 아니다.

## 1-4. 선택의 효과가 불균등하고 함정이 있다 `[측정]`

이전 배치 실행 결과다. 각 조건 40경기.

| 준비 선택 | 공격 승률 | 라운드 길이 |
|---|---|---|
| 준비 미지정 | 58% | 75초 |
| 선발조 0명 · 단일 진입 | 33% | 83초 |
| 분산 진입 3+2 | 23% | 74초 |
| 선발조 3명 · 70초 수색 | 8% | 150초(시간 만료) |
| 선발조 2명 · 40초 수색 | **0%** | 150초(시간 만료) |

"직관적인 선택"의 전제는 **선택이 대체로 비슷하게 유효하고, 취향에 따라 갈리는 것**이다. 지금은 화면에 나란히 놓인 선택지 중 하나가 승률 0%다. 유저가 직관으로 고르면 절반은 확정 패배를 고른다.

원인은 이전 QA의 P0-01(선발조 합류 좌표가 전원 동일해 재진입 국면 전환이 성립하지 않음)이고 아직 수정되지 않았다.

## 1-5. 관전 화면의 정보량도 시뮬레이션급이다 `[화면]`

한 화면에 동시에 표시되는 것.

- 스코어보드 + 생존 표식 10개
- ENEMY INTEL 5칸 (식별/미확인)
- 킬피드 (최대 4줄 이상)
- 선수 카드 5개 (이름·오퍼레이터·가젯·HP 바)
- 선택 선수 상세 (국가/오퍼레이터/무기/HP 숫자/탄약 숫자)
- 필드 라벨 (콜사인, 마지막 목격, 장거리 위험 경고, 현재 목표)
- 감독 지시 버튼 5개
- 배속·시점 컨트롤 4개

관전만 하는 게임의 화면은 **지금 무슨 일이 일어났는지**만 전달하면 된다. HP 숫자와 탄약 숫자는 조작할 수 없는 값이고, 경고 라벨은 이미 선수가 알아서 대응하는 내용이다.

## 1-6. 방향 A로 갈 때의 권고

세부 설계가 아니라 판단 기준만 적는다.

**선택을 3개로 줄인다.** 12,480가지를 유지하면서 UI만 정리하는 것으로는 해결되지 않는다. 예: 진입 방향 / 교전 태도 / 정보 우선순위 세 축, 각 3~4지, 총 27~64가지.

**각 선택을 숫자가 아니라 장면으로 표현한다.** "조준 96 / 반동 제어 67"이 아니라 "긴 사선에서 먼저 쏜다 / 문을 열고 바로 들어간다"처럼, 선택하면 **경기에서 볼 장면**을 말로 약속한다. 이미 `기대하는 장면` / `감수할 위험` 필드가 있으니 그것을 전면으로 올리면 된다.

**모든 선택은 대체로 유효해야 한다.** 승률 0%인 선택지는 존재해서는 안 된다. 선택 간 승률 격차 목표를 정하고(예: 최대·최소 차이 15%p 이내) 배치 실행으로 검증한다.

**경기 중 조작은 배속과 시점만 남긴다.** 지시 버튼을 제거하고, 그만큼 준비 화면의 선택이 경기에 어떻게 반영됐는지 보여주는 쪽에 투자한다. 예: 라운드 종료 후 "당신의 선택 → 실제로 벌어진 일" 대조.

**공개 숫자를 0~2개로 줄인다.** 숫자를 지우는 대신 그 선수가 어떤 장면을 만드는지 한 줄로 쓴다. 이미 `동료 우선`, `신중한 확인` 같은 성향 이름이 있으니 그것만 남기면 된다.

# 2부. 총기 파지 — 정확한 원인

"캐릭터가 총을 이상하게 쥔 것처럼 보인다"의 원인은 새 총기 원화가 아니다. **총을 몸에 붙이는 기준점이 옛 측면 원화 값을 그대로 쓰고 있다.**

## 2-1. 원인 `[코드]`

이번 패치에서 `weaponParts.ts`는 새로 작성됐지만 **`operatorVisuals.ts`는 바뀌지 않았다.**

```
git diff --stat 6fcded0..319c199 -- '*operatorVisuals*' '*weaponParts*'
 .../src/components/weaponParts.ts | 105 +++++++++++----------
 1 file changed, 54 insertions(+), 51 deletions(-)
```

`minimalOperator.ts`는 총기 위치를 이렇게 잡는다.

```ts
const muzzle = muzzlePosition(unit.callSign, unit.position, unit.facing);
const dx = muzzle.x - unit.position.x, dy = muzzle.y - unit.position.y;
const tip = { x: dx*c + dy*s, y: -dx*s + dy*c };   // 몸통 로컬 좌표
...
ctx.translate(tip.x, tip.y); paintWeaponPart(ctx, unit.weaponName, _asset);
```

그리고 `operatorVisuals.ts`의 `muzzlePosition`은 여전히 이렇다.

```ts
const visual = operatorVisual(callSign);            // 폐기된 측면 아틀라스
const x = visual ? (visual.muzzle[0] - visual.pivot[0]) * OPERATOR_SCALE : ...;
const y = visual ? (visual.muzzle[1] - visual.pivot[1]) * OPERATOR_SCALE : 0;
```

**측면에서 본 인물 원화의 픽셀 앵커**로 총구 위치를 계산한다. 그 원화는 더 이상 그리지 않는다. 새 탑뷰 PNG는 총구를 원점에 두고 그려지므로, 총 전체가 옛 측면 좌표를 따라 배치된다.

## 2-2. 결과 `[측정]`

실제 상수로 계산한 값이다. 몸통 폴리곤은 12명 전부 동일하게 `x −18 ~ +7`(길이 25), 어깨는 `y ±10`.

| 오퍼레이터 | 총구 x | 총 길이 | 개머리판 x | 몸 뒤로 삐짐 | 총 중심선 y | 방아쇠손 x |
|---|---|---|---|---|---|---|
| HALLORAN | 30.3 | 57 | −26.8 | **+8.8** | +0.88 | **−7.5** |
| MEDVED | 22.8 | 44 | −21.2 | **+3.2** | −1.32 | **−7.0** |
| REUSS | 27.2 | 48 | −20.8 | **+2.8** | −1.98 | −3.8 |
| BRANDT | 32.7 | 53 | −20.3 | **+2.3** | −0.66 | −3.6 |

### (1) 총이 몸 정중앙을 관통한다 — 가장 큰 원인

**총 중심선 y가 12명 전부 −1.98 ~ +0.88이다. 즉 0이다.**

위에서 내려다본 사람이 소총을 들면, 총은 한쪽 어깨 앞(로컬 `y ≈ +6~9`)에 붙어 몸의 중심선과 **나란히 비켜서** 있어야 한다. 지금은 총이 몸 중심선 위에 정확히 겹쳐 있어서, 개머리판이 몸통 가운데에 꽂힌 것처럼 보인다. 확대해서 보면 총이 등에 X자로 걸린 것처럼 읽힌다.

### (2) 개머리판이 몸 뒤로 튀어나온다

몸통 뒤끝이 `x = −18`인데, 6명은 개머리판이 그보다 더 뒤에 있다. HALLORAN은 **8.8단위(0.22m)** 삐져나온다. 총 길이 57, 몸 길이 25 — 총이 몸의 2.3배이고 앞뒤로 균등하게 튀어나와 "꼬치에 꿰인" 형태가 된다.

### (3) 방아쇠손 위치가 오퍼레이터마다 14단위 다르다

방아쇠손 x가 **−7.5(HALLORAN) ~ +7.6(MARCHAND)** 로 흩어진다. 몸은 12명 전부 같은데 손 위치만 다르다. HALLORAN과 MEDVED는 방아쇠손이 몸 중심보다 7단위 **뒤**에 있다. 등 뒤에서 총을 쥐고 있는 모양이다.

## 2-3. 부수 문제

**팔꿈치가 기하학적으로 계산되지 않는다** `[코드]`

```ts
hands.forEach((hand, i) => arm(i ? 1 : -1, { x: hand.x * .5, y: (i ? 10 : -10) + 3 }, hand));
```

팔꿈치 x는 손 x의 절반, y는 ±13 고정이다. 상완·전완 길이를 지키지 않으므로 총구 오프셋이 19~33으로 다른 만큼 **팔 길이도 오퍼레이터마다 달라진다.** 또 손 y가 0~2.6인데 어깨는 ±10이라 양팔이 중앙으로 모여 총을 껴안는 모양이 된다.

**손이 너무 작다** `[코드]` `[화면]`

```ts
ctx.ellipse(hand.x, hand.y, 2.5, 2.1, 0, 0, Math.PI*2);
```

어깨폭 25단위 캐릭터에서 손이 5단위다. 추적 시점 배율(약 1px/단위)에서 5px이라 "쥐었다"는 신호가 화면에서 보이지 않는다. 4배로 확대해서야 확인됐다.

**군장 파츠가 별 모양으로 읽힌다** `[화면]`

뒤로 보이는 부츠 폴리곤(`rear = −22`)과 군장 박스들(`x −19~−3`, `y +9~+18`)이 몸 둘레로 삐져나와, 확대 화면에서 뾰족한 톱니 별처럼 보인다. 사람 윤곽이 아니다.

## 2-4. 수정 방향

핵심은 하나다. **총구 위치를 오퍼레이터가 아니라 어깨 위치와 총기 길이로 정한다.**

```ts
// 탑뷰: 총은 오른어깨 앞 한 지점에서 나가고, 총구 거리는 총기 길이가 정한다.
// 오퍼레이터별 옛 측면 원화 앵커는 더 이상 사용하지 않는다.
const SHOULDER = { x: 4, y: 7 };          // 몸통 로컬 좌표. 몸통은 x −18~+7, 어깨 y ±10
export function muzzleOffset(weaponName: string): TacticalPoint {
  const part = weaponPart(weaponName);
  // 개머리판이 몸 뒤끝(−18)을 넘지 않도록 총구 전방 거리를 총 길이에서 역산한다.
  return { x: Math.min(SHOULDER.x + part.length * 0.62, part.length - 18), y: SHOULDER.y };
}
```

이 한 함수를 바꾸면 (1)(2)(3)이 함께 해결된다. 총 중심선이 `y = 7`로 어깨 앞에 놓이고, 개머리판이 몸 뒤로 넘지 않으며, 손 위치가 총기 길이에만 의존하므로 오퍼레이터별 편차가 사라진다.

**주의 — 엔진과 공유되는 값이다.** `muzzlePosition`은 렌더뿐 아니라 엔진의 발사 원점으로도 쓰인다(코드 주석: "판정과 중계가 같은 발사 원점을 사용합니다"). 이 불변조건은 유지해야 하므로 **렌더용과 엔진용을 따로 만들지 말고 한 함수를 고쳐 양쪽이 함께 따라가게 한다.** 발사 원점이 몇 단위 이동하므로 전투 관련 스위트(`realtime-regression`, `combat-overhaul`, `tactical-counters`, `weapon-presentation`)를 재실행해 판정 변화를 확인해야 한다.

함수 시그니처가 `callSign` 기준에서 `weaponName` 기준으로 바뀐다. 호출부에 `unit.weaponName`이 이미 있으므로 치환은 기계적이다.

부수 항목은 그 다음이다.

- 팔꿈치를 상완 9 · 전완 8 길이를 지키는 2관절 역기구학으로 계산한다. 이미 `throwArmPose`가 같은 방식을 쓰고 있으니 그 코드를 재사용한다
- 손 반지름을 2.5 → 4로 올린다
- 군장 파츠를 몸 윤곽 안쪽으로 넣거나 개수를 줄인다

## 2-5. 검증 방법

저장소에 이미 `validation/weapon-eight-directions.png`와 `validation/individual-weapons.png`가 있고 `tests/weapon-presentation.cjs`가 생성한다. 수정 후 같은 스크립트를 다시 돌려 **8방향 전부에서**

- 총 중심선이 몸 중심선과 겹치지 않는지
- 개머리판이 몸 뒤끝을 넘지 않는지
- 방아쇠손이 어깨와 총 사이에 있는지

를 눈으로 확인한다. 12종 × 8방향 비교 이미지가 이미 나오므로 추가 도구는 필요 없다.

## 부수 관찰 — 이번 플레이에서

라운드가 **2:30에서 2:21에 종료됐다.** 9초 만에 공격팀 전원이 이탈했고, 킬피드는 이렇다.

**1부의 "직관적인 선택"과 직접 연결되는 문제다.** 준비 화면에서 무엇을 고르든 9초에 라운드가 끝나면 그 선택은 경기에 반영될 시간이 없다. 선택이 의미를 갖기 위한 선행 조건은 라운드가 충분히 지속되는 것이고, 그것은 교전 치명성 조정이다.
